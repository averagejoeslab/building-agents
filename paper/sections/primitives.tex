\section{The Primitives}
\label{sec:primitives}

Each primitive is defined by what it does and by what it never does. The negative definitions make the five mutually exclusive: every piece of a harness has one home, assigned by its function rather than by its name or its location in the code. Table~\ref{tab:primitives} collects the definitions.

To show each primitive rather than describe it, we use five programs, each the previous one plus one primitive, all run on the same task: a two-file Python project whose \texttt{total()} subtracts a discount as a flat amount where the test expects a percentage, and the request \emph{``The tests are failing. Find out why and fix it.''} The model is Claude Sonnet through Anthropic's Messages API. The complete programs are in Appendix~\ref{app:minimal}; the excerpts below are the lines each primitive adds. In the transcripts, \texttt{>} is what the person typed, \texttt{<} what the model said, and \texttt{\$} a command it ran.

\subsection{\prim{Model interface}: reach the model}
\textbf{Does.} Send the assembled context to the model and bring back its response in a form the rest of the harness can read: words, and structured requests to act. The client, the wire format, the translation to the model's chat template, streaming, retries, and switching to a backup model when a request could not be served.
\textbf{Never.} Decide what the request contains (\prim{Context}). Act on the response (\prim{Output}).

\lstinputlisting[firstline=4]{minimal/1_model_interface.py}
The model answers, but it can only answer: \emph{``I don't have access to your code, test files, or test output. Nothing came through in your message besides the request.''} The request is written into the program, so nobody can ask it anything else.

\subsection{\prim{Input}: capture what comes in}
\textbf{Does.} Capture what enters the agent and hand it to \prim{Context}. Two sources: a person (a message, a file, an interrupt, an answer to a question the model asked) and the world (the result of an action, an event, a scheduled trigger).
\textbf{Never.} Decide what the model is shown (\prim{Context}). Run anything (\prim{Output}).

\lstinputlisting[firstline=4,linerange={11-16}]{minimal/2_input.py}
Anyone can now type the request, and the answer is the same: \emph{``I don't have the code or the test output yet, so I can't tell why the tests are failing. Could you share\ldots''} It can only talk.

\subsection{\prim{Output}: carry the response out}
\textbf{Does.} Handle what the model returned: show its words to a person, and carry out each requested action, collecting its result. The tool set, the executor that runs an action, and the environment it runs in.
\textbf{Never.} Decide whether to go again (\prim{Control flow}). Assemble the next request (\prim{Context}). The model only ever \emph{requests} an action; \prim{Output} decides whether and how it happens, which is where sandboxes and never-lists live.

\lstinputlisting[firstline=4,linerange={6-26}]{minimal/3_output.py}
A tool is described to the model, and \texttt{handle\_output} runs each command the model asks for and collects the result:
\begin{lstlisting}[language={},basicstyle=\ttfamily\scriptsize,breaklines=true,breakindent=1.5em,frame=none,commentstyle=\ttfamily,keywordstyle=\ttfamily,stringstyle=\ttfamily]
> The tests are failing. Find out why and fix it.
< I'll start by exploring the project and running the tests.
$ pwd; ls -la; git status 2>/dev/null | head
\end{lstlisting}
Then it stops. The command ran and printed the files, and the result went nowhere.

\subsection{\prim{Control flow}: decide what happens next}
\textbf{Does.} Define the shape of the loop: send results back and go again, hand back to the person, or stop. Step and token budgets, approval gates the harness consumes, delegation to sub-agents, and routing to a model keyed to the work.
\textbf{Never.} Capture input, assemble context, call the model or run a tool. It sequences the other four.

\lstinputlisting[firstline=4,linerange={31-41}]{minimal/4_control_flow.py}
With the results sent back and the model called again until it stops requesting actions, the same model, tool and request finish the task:
\begin{lstlisting}[language={},basicstyle=\ttfamily\scriptsize,breaklines=true,breakindent=1.5em,frame=none,commentstyle=\ttfamily,keywordstyle=\ttfamily,stringstyle=\ttfamily]
> The tests are failing. Find out why and fix it.
< Let me start by looking at the project and running the tests.
$ pwd; ls -la; git status 2>/dev/null | head
$ cat prices.py test_prices.py; python -m pytest -q 2>&1 | tail -30
$ python -m unittest -v 2>&1 | tail -20
< The docstring says the discount is a percentage, but the code subtracts it
  as a flat amount. So 25 - 10 = 15 instead of 25 x 0.9 = 22.5. I'll fix the
  code to match the documented behavior.
$ sed -i 's|return round(subtotal - discount, 2)|return round(subtotal * (1 - discount / 100), 2)|' prices.py && cat prices.py && python -m unittest 2>&1 | tail -5
< The tests pass now. The bug was in prices.py, not in the tests.
\end{lstlisting}
This is an agent. Asked a question about itself, it has to go looking:
\begin{lstlisting}[language={},basicstyle=\ttfamily\scriptsize,breaklines=true,breakindent=1.5em,frame=none,commentstyle=\ttfamily,keywordstyle=\ttfamily,stringstyle=\ttfamily]
> Who are you, and where are you working?
< I'll check the environment first so I can answer accurately.
$ echo "user: $(whoami)"; echo "host: $(hostname)"; echo "cwd: $(pwd)"; uname -a; ls -la | head -20
< I'm an AI assistant. I can run shell commands, and I use that to read files,
  run code and make changes in the environment I'm given.
\end{lstlisting}
It does not know its name, its body, its working directory or the date.

\subsection{\prim{Context}: assemble what the model is shown}
\textbf{Does.} Assemble, for one call, everything the model is shown: instructions, the tools' descriptions, the conversation so far, and anything retrieved from memory or the environment; and fit it to the window by truncation, compaction or selection. \prim{Context} is the agent's working memory, rebuilt on every call.
\textbf{Never.} Call the model (\prim{Model interface}). Act on the world (\prim{Output}). Reading a memory store is \prim{Context}; writing one, if the model requests it, is an action and so \prim{Output}.

\lstinputlisting[firstline=4]{minimal/quark.py}
One sentence of context, assembled on every call, answers the question without any action:
\begin{lstlisting}[language={},basicstyle=\ttfamily\scriptsize,breaklines=true,breakindent=1.5em,frame=none,commentstyle=\ttfamily,keywordstyle=\ttfamily,stringstyle=\ttfamily]
> Who are you, and where are you working?
< I'm quark, an agent that works by running shell commands through bash. My
  working directory is /tmp/shop. Today's date is 2026-10-07.
\end{lstlisting}
This is the whole harness: fifty lines, five functions, one per primitive. It runs commands on the host without asking and forgets everything when it exits; the production concerns of \S\ref{sec:levels} are what it lacks.

\paragraph{Each primitive removes a failure the others do not.} With only \prim{Model interface}, the model answers but cannot act and nobody can ask it anything else; with \prim{Input}, anyone can ask and it still cannot act; with \prim{Output}, it acts once and the result goes nowhere; with \prim{Control flow}, it finishes the task but spends actions finding out where it is; with \prim{Context}, it knows. The same five programs, run with a local model in place of the hosted one, needed one function changed: \texttt{request\_response}, which is \prim{Model interface}. That is the porting property of \S\ref{sec:vocabulary} in practice.
