\section{Three Levels: Primitive, Design Decision, Production Concern}
\label{sec:levels}

Descriptions of harnesses mix three kinds of statement. ``It has a loop'' names a primitive. ``It gives the model forty tools'' names a decision within one. ``It runs commands in a sandbox'' names a measure taken for a reason that applies to every primitive. Keeping the three apart is the main use of the vocabulary, and the deconstruction in \S\ref{sec:deconstruction} records each component at its level.

\paragraph{Primitives.} A primitive is a mechanism every harness has, defined by its function on the request path (\S\ref{sec:primitives}). A harness has exactly five. A harness that lacks one is not an agent's harness, or is not a harness.

\paragraph{Design decisions.} A design decision is one way of implementing a primitive. It is the level at which harnesses differ, and the level at which they are usually described: a single shell tool or a set of file tools (\prim{Output}); a repository map or a project file in the instructions (\prim{Context}); a loop that runs until the model stops or a graph with named nodes (\prim{Control flow}); one provider or a gateway to many (\prim{Model interface}); a terminal or a message queue (\prim{Input}). A design decision never adds a primitive; it fills one. The test for whether something is a design decision is whether a different harness could make a different choice and still be a harness.

\paragraph{Production concerns.} A production concern is a question asked of every primitive, whose answer changes how some primitives are implemented. We use six (Table~\ref{tab:concerns}): what should outlast the session (persistence); what could do harm, and who could make it (safety and security); what did it do (observability); what if something breaks (resilience); what is slow or costly (performance); and how do we know it still works (evaluation). A concern is not a part of the harness. A sandbox is not a sixth primitive; it is the safety answer in \prim{Output}. A memory store is not a sixth primitive; it is the persistence answer in \prim{Context} and \prim{Output}. The test for whether something is a concern is whether it is motivated by a question that could equally be asked of a different primitive.

\paragraph{The concerns interact.} Persistence creates a security surface: a poisoned memory steers every later session. Streaming changes safety: an interrupt can stop a reply mid-sentence, and the harness must record what was said rather than a finished answer. Summarizing changes persistence: the summary must say where the originals are kept. Treating concerns as questions asked of each primitive makes these interactions visible; treating them as separate components hides them.

\subsection{Rules for the cases at the boundaries}
\label{sec:rules}
The negative definitions decide most cases. The following rules decide the rest. Each was needed for a component found in \S\ref{sec:deconstruction}.

\begin{description}
  \item[Function, not location.] A component is assigned by what it does, not by the file or the name it has. Code inside a tool that decides what the model sees is \prim{Context}. An approval decision made inside a tool's runtime is \prim{Control flow}.
  \item[The tool channel.] The model drives other primitives through tool calls: spawning a sub-agent, entering a planning mode, writing a plan, searching for tools, asking the person a question. The call is \prim{Output}; its effect is assigned to the primitive it changes.
  \item[Backup versus routing.] A model change triggered by a request that could not be served is \prim{Model interface}. A model change keyed to the work is \prim{Control flow}. A fixed model for one class of request, such as compaction summaries, is a request setting and \prim{Model interface}.
  \item[Receiving versus rendering.] Receiving a response as a stream is \prim{Model interface}; rendering each fragment is \prim{Output}.
  \item[Parallel actions versus parallel calls.] Several tool calls from one response run concurrently: \prim{Output}. Several model calls issued concurrently, to divide a task or to vote: \prim{Control flow}.
  \item[The reader of a record.] A record kept for the model (a searchable transcript) is \prim{Context}. A record kept for the operator (a trace) is observability. An artifact for the user (a diff view) is \prim{Output}. One file may serve several readers, and each use is assigned separately.
  \item[The consumer of an answer.] An answer the harness consumes (an approval) is \prim{Control flow}. An answer the model consumes (the result of an ask-the-user tool) is \prim{Input}.
  \item[Direct actions by a person.] A command the person runs through the harness's own executor, whose output enters the conversation, is \prim{Input}, although it reuses \prim{Output}'s executor.
  \item[Model-written programs.] A program the model writes at run time is \prim{Control flow} if it sequences model calls and \prim{Output} if it sequences only tools.
  \item[Bundles.] A mode, a skill, a hook system or an agent profile is packaging that bundles decisions across several primitives. Decomposed, each element has one home: a planning mode is a context template, a restricted tool set and an approval gate; a hook system is a dispatcher (\prim{Control flow}) whose events each affect one primitive.
  \item[Nested harnesses.] A sub-agent is a harness of its own, and delegation to it is \prim{Control flow} of the outer harness. The same holds for model-backed components inside a harness, such as an approval reviewer or a termination judge: each is \prim{Control flow} with a \prim{Model interface} call.
  \item[Tool protocols.] A protocol such as MCP \citep{mcp} provides pluggable \prim{Output} (third-party tools). Its other features are assigned by function: resources and prompts are \prim{Context}; sampling borrows the client's \prim{Model interface}; elicitation is \prim{Input}.
\end{description}
