\section{Deconstruction of Six Harnesses}
\label{sec:deconstruction}

If the position holds, a harness built by someone else, for a different purpose, at a different scale, should decompose into the five primitives with nothing left over, and its differences from other harnesses should be locatable as design decisions within a primitive. We test this on six.

\paragraph{Selection.} We chose harnesses in wide use whose primary sources were available, across three kinds: two command-line coding agents from model developers (Claude Code \citep{claudecode} and Codex CLI \citep{codexcli}), two open-source coding agents built outside the model developers (opencode \citep{opencode} and pi \citep{pi}), one general-purpose agent built for messaging platforms as well as the terminal (Hermes Agent \citep{hermes}), and one workflow framework (LangGraph \citep{langgraph}), for which we deconstruct the canonical agent it ships, a ReAct loop, together with the runtime that executes it. The workflow framework is included to test the claim that a workflow and an agent differ only in \prim{Control flow}. Five of the six publish their source; Claude Code does not, and is deconstructed from its documentation. The six are not a sample of all harnesses, and \S\ref{sec:limitations} says what that leaves untested.

\paragraph{Method.} For each harness we (i) read the source at a pinned commit, or the documentation on a stated date, and mapped the path of a request from the moment a message arrives to the next model call; (ii) assigned every component on that path to exactly one primitive, or to one production concern together with the primitive it changes, by the definitions of \S\ref{sec:primitives} and the rules of \S\ref{sec:rules}, citing a file and line range or a page and section for each; and (iii) recorded every component that was hard to place and how it was resolved, or that it was not. Components outside the request path (hosting, packaging, UI frameworks) were noted and left unassigned. The evidence is in Appendix~\ref{app:evidence} and in the repository as a file per harness; the subsections below summarize it.

\paragraph{What was hard to place.} The hard cases are collected in Appendix~\ref{app:evidence}, and four recur across harnesses.
\begin{itemize}
  \item \textbf{Primitives that call the model.} In Claude Code, opencode and pi, compaction decides what to summarize and then calls the model to summarize it; Claude Code's web-fetch tool and pi's code mode call models from inside a tool. Read as a call graph, these break the rule that \prim{Context} and \prim{Output} never call the model. Read as responsibility, they do not: the component still decides one thing, and uses \prim{Model interface} to do it. We added the rule on primitives as services (\S\ref{sec:rules}) for these cases.
  \item \textbf{Approval gates inside tools.} In opencode and Hermes the code that asks the person sits inside the tool that would act, and in Codex the approval requirement depends on what the sandbox allows. By function the gate is \prim{Control flow} and the enforcement is \prim{Output}; by location they are one file. The two also read each other, which is the interaction of concerns noted in \S\ref{sec:levels}.
  \item \textbf{Decisions carried out by editing the context.} opencode enforces a step budget by appending an assistant message and disabling tools; Hermes's stop gates append a synthetic message and go again; LangGraph replaces the model's answer with a canned message when the step budget is reached. Each is a \prim{Control flow} decision whose mechanism is a change to what the model is shown. The decision and the mechanism have different homes, and we record both.
  \item \textbf{Nesting at the model interface.} Hermes can hand a whole turn to an external Codex process, or reach an agent over ACP as if it were a model. The thing behind \prim{Model interface} is then another harness. The nested-harness rule covers it, but the nesting is at a different primitive from the sub-agent case, and the outer harness keeps only \prim{Input}, persistence and a fallback.
\end{itemize}
One finding is not a hard case but a boundary question. Claude Code's server-side classifier runs inside the API during the session's own requests, and opencode can delegate compaction to the provider. In both, a function the vocabulary places in the harness runs on the provider's side of the API, and the local harness holds only a verdict or an opaque item. The primitives still apply: the harness is split across two machines, not reduced to four parts. But it means the boundary of \S\ref{sec:boundary} is at the model's weights, not at the API, and a deconstruction from a client's source alone will miss the part that runs behind the API. We found no component in the six that satisfied none of the five definitions.
