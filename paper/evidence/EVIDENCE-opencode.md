# OpenCode

**Source:** https://github.com/anomalyco/opencode · **Version:** commit 654b79b27e79da735d6b07d766c8d7431a71d1b7 (2026-10-15); `@opencode/core` package version 2.0.29 · **Language:** TypeScript (Bun runtime, Effect 4 library)
**Path conventions:** `core/` = `packages/core/src/`, `ai/` = `packages/ai/src/`, `schema/` = `packages/schema/src/`, `codemode/` = `packages/codemode/src/`, `server/` = `packages/server/src/`, `recorder/` = `packages/http-recorder/src/`. Line ranges are `Lstart–Lend` at the pinned commit. Note: the brief's expected layout (`packages/opencode/src/session/prompt.ts`, `processor.ts`, `llm.ts`, `system.ts`) no longer exists at this commit; the equivalents are `core/session/prompt.ts` (input preparation), `core/session/runner/llm.ts` (the loop), `core/session/runner/step.ts` (one model call plus its tools), `core/session/model-request.ts` (request assembly), `core/session/compaction.ts`, `core/session/system-prompt.ts`.
**What it is:** OpenCode is an open-source coding agent harness by Anomaly (anomalyco) that runs as a local server with TUI, desktop, and web clients; a session is a durable, event-sourced record in SQLite that a per-session "runner" fiber drains step by step. The model is reached through the in-house `@opencode/ai` client, which compiles a canonical `LLMRequest` into a provider protocol (Anthropic Messages, OpenAI Responses, Bedrock Converse, Gemini, …) over HTTP/SSE or a stateful WebSocket, with a Vercel AI SDK bridge for third-party provider packages.

## Control flow
- **Entry: `Session.prompt` admits input then rings the doorbell:** reconciles the inbox row, prepares the prompt, admits it, and calls `execution.wake(sessionID)` unless `resume === false`. `core/session/session.ts:L145–L178`
- **Run coordinator (one execution fiber per session):** `loop` drains, then re-drains while a `pendingWake` doorbell was rung mid-drain; `wake` coalesces scopes ("input" subsumes "steer"); `interrupt` marks `stopping`, claims recorded wakes and interrupts the owner fiber. `core/session/run-coordinator.ts:L74–L85`, `L136–L145`, `L147–L167`
- **Execution service routes drains and handles `DrainResult`:** `Complete` ends, `Moved` and `Reloaded` re-enter `drain` with a continuation step. `core/session/execution.ts:L87–L110`; `DrainResult` enum `core/session/runner/index.ts:L23–L28`
- **The outer loop (`SessionRunner.drain`):** `while (true) { next = advanceToStep(); if not Ready return; continuing = runStep(ctx, step); step++ }`. `core/session/runner/llm.ts:L191–L198`
- **Step boundary (`advanceToStep`):** at each boundary the runner checks `lifecycle.isClosed()`, pulls the next inbox item under a per-session lock, handles `compaction` and `move` controls inline, and otherwise promotes pending steers/queued input before loading context; a promoted input resets `step = 1`. `core/session/runner/llm.ts:L74–L189`
- **Steer vs queue delivery:** `Promotable` doc: "steer" promotes steers only (mid-work), "input" also admits one queued item at an idle boundary. `core/session/inbox.ts:L43–L48`; `nextPromotable` `L407–L424`; `promote` `L496–L531`; a pending compaction is pulled ahead of earlier steers `L533–L550`; `Delivery = "steer" | "queue"` `schema/session-inbox.ts:L11`
- **Inner step policy (`runStep`):** before every attempt it runs auto-compaction (`compacted.status === "completed"` → new assistant id and `continue`), then prepares the request and dispatches on the attempt `Outcome`. `core/session/runner/llm.ts:L209–L330`
- **Stop condition:** `needsContinuation = toolChoice !== "none" && record.needsContinuation` (a step with executed tool calls continues; a text-only finish hands back); `finish === "length"` → `OutputLimit`. `core/session/runner/step.ts:L281–L283`
- **Step budget:** `stepLimitReached = agent.info.steps !== undefined && step >= agent.info.steps`; on the final step the runner appends `MAX_STEPS_PROMPT` as an assistant message and sets `toolChoice: "none"` while keeping tool definitions to preserve the cached prefix. `core/session/runner/llm.ts:L226–L247`; prompt text `core/session/runner/max-steps.ts:L1–L16`; `steps` field `schema/agent.ts:L33`; tool calls on that step fail with "Tools are disabled after the maximum agent steps" `core/session/runner/step.ts:L91–L101`
- **Output-limit continuation:** after `finish === "length"` the runner reads the last 3 user/assistant rows; if all three are assistant `length` finishes it fails with `output-limit`, else publishes the synthetic `CONTINUE_AFTER_OUTPUT_LIMIT` and goes again. `core/session/runner/llm.ts:L290–L319`; constant `L38–L39`
- **Interrupted-stream continuation:** `Continue` outcome waits the retry delay, publishes `CONTINUE_AFTER_INCOMPLETE_STREAM` and starts a fresh assistant message. `core/session/runner/llm.ts:L281–L289`; constant `L35–L36`
- **Retry wait is part of the loop:** `Retry` outcome → `retry.wait` (publishes `RetryScheduled`, sleeps) then the `while (true)` re-attempts with refreshed context. `core/session/runner/llm.ts:L275–L280`, `L216–L219`; `wait` `core/session/runner/retry.ts:L97–L113`
- **Overflow → compact → go again:** `Compacted` outcome sets `recoverOverflow = false` (one overflow compaction per step) and re-attempts. `core/session/runner/llm.ts:L265–L271`, `L320–L323`
- **Approval gate consumed by the harness:** `Permission.assert` evaluates rules (`deny` → `BlockedError`, `allow` → continue, `ask` → create request and await a `Deferred`). `core/permission.ts:L231–L263`; the reply endpoint resolves it, `"always"` persists a rule, a `reject` with no message fails every pending ask in the session. `core/permission.ts:L265–L325`
- **A decline ends the step:** declined tool calls are failed with "The user declined this tool call" and the attempt is interrupted (`Effect.interrupt`) rather than returned to the model. `core/session/runner/step.ts:L207–L215`, `L274–L277`
- **Interrupt with resume:** after interrupting, if the next promotable item is a steer or a control, the coordinator is woken with scope "steer" so queued next-turn prompts stay parked. `core/session/execution.ts:L153–L170`
- **Sub-agent delegation (outer-harness side):** the `subagent` tool walks `parentID` to compute depth and refuses beyond `experimental.subagent_depth` (default 1); it creates a child session with `parentID`, prompts it, and in foreground blocks on the child's job; background returns immediately. `core/tool/plugin/subagent.ts:L117–L133`, `L185–L198`, `L205–L218`, `L229–L240`
- **Child session is a harness of its own:** the job's `run` is `sessions.resume(childSessionID)` and the result is the text of the last completed assistant message. `core/session/subagent-job.ts:L45–L63`
- **How results return:** foreground → tool result text wrapped in `<subagent sessionID=… state="completed">`; background → a synthetic user message delivered to the parent when the job settles. `core/tool/plugin/subagent.ts:L252–L266`; `core/session/subagent-completion.ts:L21–L46`
- **Routing to a cheap model keyed to the work (title):** the title agent uses `model.small(primary.providerID)` plus a minimal-reasoning variant (`none|minimal|low`), forked so it never delays the step. `core/session/context.ts:L95–L119`, `L186`; fork `core/session/runner/llm.ts:L177–L180`
- **Compaction model keyed to the work:** the `compaction` agent may carry its own model; otherwise the session model is used. `core/session/compaction.ts:L213–L219`
- **Agent profiles (bundles):** `build` (default, all-allow + question), `general`/`explore` sub-agents with deny lists and a custom system prompt, hidden `compaction`/`title`/`summary` agents. `core/plugin/agent.ts:L80–L140`; default ruleset `schema/agent.ts:L46–L51`
- **Plan mode (bundle):** a `plan` agent denies `edit` outside `~/.opencode/plan/*` (control flow), rewrites blocked-edit errors (output), and re-injects a `<system-reminder>` per request (context). `core/plugin/plan.ts:L33–L42`, `L44–L53`, `L57–L60`
- **Crash/restart resume:** at boot, sessions whose execution claim survived are resumed with a synthetic "The server restarted…" notice; a durable per-turn counter stops after `DEFAULT_MAX_ATTEMPTS = 10`. `core/session/execution/restart.ts:L77–L99`, `L193–L231`; budget `L33`

## Input
- **HTTP handler → `session.prompt`:** `text`, `files`, `agents`, `skills`, `metadata`, `delivery`, `resume` are passed straight through. `server/handlers/session.ts:L307–L322`
- **Prompt preparation (`SessionPrompt.prepare`):** fires the plugin hook `session.prompt` (plugins may rewrite text/files/delivery), materializes attachments with concurrency 8, resolves `skills` to their text, and builds a `UserPayload`. `core/session/prompt.ts:L29–L91`
- **Attachments:** `data:` URLs or `file:` URIs; 20 MiB cap; `?start=&end=` line ranges for text; a directory becomes a sorted listing. `core/session/prompt.ts:L93–L133`, `L151–L201`, `L203`
- **Image normalization on input:** images are resized via `Image.Service` (resizer unavailable → passthrough). `core/session/prompt.ts:L135–L149`
- **Durable admission:** the inbox row is inserted into SQLite (`admit`, `reconcile`, `cancel`, `steer`, `queue`). `core/session/inbox.ts:L155`, `L169`, `L230–L256`, `L295`
- **Harness-originated input (synthetic):** `Session.synthetic` admits text the harness produced (restart notice, job completions) through the same inbox. `core/session/session.ts:L273–L314`
- **Answer the MODEL consumes (question tool):** the form answers are rendered as `User has answered your questions: …` and returned as the tool result. `core/tool/plugin/question.ts:L38–L46`, `L62–L112`
- **Background shell completion event:** `notifyWhenDone` waits on the job and admits a synthetic message with the output. `core/tool/plugin/shell.ts:L157–L189`
- **Sub-agent completion event:** delivered as a synthetic message tagged `<subagent … state=…>`. `core/session/subagent-completion.ts:L37–L44`

## Context
- **Selection (`SessionContext.select`):** fixes session, agent, tool snapshot (narrowed by merged agent+session permissions) and instruction sources, loaded in parallel. `core/session/context.ts:L121–L161`; permission narrowing `L131`
- **Instruction ordering for cache reuse:** "Ordered from most to least shared across sessions so the baseline stays a reusable prompt-cache prefix": Code Mode catalog, MCP, references, skills, AGENTS.md discovery, builtins (date/env), per-session entries. `core/session/context.ts:L147–L158`
- **Load (`SessionContext.load`):** resolves the model and reads history after the latest replayable compaction. `core/session/context.ts:L163–L179`
- **System prompt assembly:** `[agent.system ?? default prompt rendered with tool guidance, initial instructions]`; messages via `toLLMMessages`. `core/session/model-request.ts:L100–L120`
- **Default system prompt text:** 15 lines ("You are an AI agent running in OpenCode…"), with `${OPENCODE_TOOL_GUIDANCE}` filled per available tool. `core/session/runner/prompt/system.txt:L1–L15`; `core/session/system-prompt.ts:L9–L28`
- **Built-in instructions:** today's date and an `<env>` block (working dir, workspace root, git, platform, tmp). `core/instructions/builtins.ts:L24–L53`
- **AGENTS.md discovery:** global `AGENTS.md` plus ancestor-walk from the location to the project root, watched for changes. `core/config/plugin/instruction.ts:L36–L62`, `L76–L86`
- **Catalogs rendered into the baseline:** skills `<available_skills>` `core/skill/instructions.ts:L16–L33`; MCP `<mcp_instructions>` `core/mcp/instructions.ts:L17–L29`; Code Mode catalog `core/codemode/instructions.ts:L9–L30`
- **Instruction epochs:** changed instruction sources are frozen into a durable `InstructionsUpdated` event with rendered delta text, so later requests see "Today's date is now…" style updates as system messages. `core/session/instruction-state.ts:L38–L61`, `L80–L87`; rendered as `Message.system` `core/session/runner/to-llm-message.ts:L291–L292`
- **History read bounded by compaction:** rows from the latest completed compaction `seq` onward; native checkpoints only when the target model can replay them. `core/session/history.ts:L21–L26`, `L78–L108`, `L118–L135`
- **Projection of history into model messages:** synthetic/skill/shell messages become `user` role; a compaction becomes a `<conversation-checkpoint>` user message. `core/session/runner/to-llm-message.ts:L269–L327`, `L330–L334`
- **Tool definitions snapshot:** tools wholly denied by permission are dropped; `codemode: false` tools are advertised directly, the rest only inside the single `execute` tool; definitions sorted by name. `core/tool.ts:L225–L287`; JSON Schema generation `core/tool/runtime.ts:L21–L27`, `L174–L188`
- **Plugin hook that rewrites what the model sees:** `session.context` sees system, messages, tool descriptions/schemas and the default `maxTokens`; renamed tools are mapped back by object identity. `core/session/model-request.ts:L236–L274`
- **Media fitting:** unsupported modalities are replaced by an ERROR text; inline images are dropped from oldest once the total exceeds 25 MiB until under 15 MiB. `core/session/model-request.ts:L43–L46`, `L132–L147`, `L189–L216`; applied `L297`
- **Output token budget fitted to the window:** `outputLimit` = min(catalog limit, 256k), reduced to the room left after `measured + estimated×1.15`, floor 1,024. `core/session/model-request.ts:L47–L57`, `L88–L98`
- **Auto-compaction trigger:** `due` when `estimateContext >= ceiling`; ceiling = window − max(10 %, 16,000) or window − configured `buffer`; skipped right after a completed compaction or before a measured response. `core/session/compaction.ts:L205–L240`, `L242–L251`, `L911–L920`; defaults `auto: true, keep: 15_000` `L197`; settings `L41–L47`
- **Prompt size estimate = provider-measured + locally estimated:** anchors on the last assistant message with a usage count from the same provider, estimates everything after at ~4 chars/token. `core/session/compaction.ts:L880–L905`, `L924–L930`, `L950–L953`
- **Summary compaction:** splits history into `older` (summarized) and `recent` (kept verbatim within `keep` tokens, starting at a user boundary); sends older + summary prompt; one template nudge before failing. `core/session/compaction.ts:L272–L316`, `L708–L744`; template `L104–L135`
- **Tool outputs in the verbatim part are cut to 1,250 chars.** `core/session/compaction.ts:L100`, `L813–L826`
- **Overflow compaction (provider said too long):** captured before any output starts, then compaction aims at 70 %/50 %/35 % of the rejected request size. `core/session/runner/step.ts:L113–L120`, `L155–L167`; `SHRINK_STEPS` `core/session/compaction.ts:L95`, `L429–L448`
- **Manual `/compact`:** an inbox control item processed at the step boundary. `core/session/session.ts:L246–L264`; `core/session/runner/llm.ts:L115–L163`
- **Native (provider-side) compaction:** for models with `compaction.type === "native"` the provider returns one opaque item that replaces the window; the harness only appends the newest user messages. `core/session/compaction.ts:L318–L332`
- **Tool result truncation before it enters history:** 2,000 lines / 50 KiB, overflow written to a file with a `[showing lines 1-N of M; full output saved to …]` marker. `core/tool-output.ts:L13–L16`, `L67–L118`; applied in the step `core/session/runner/step.ts:L127`
- **Tool input repair (what the model's call is seen as):** stringified JSON, numeric strings, placeholder nulls are repaired against the schema before execution. `core/plugin/tool-input-repair.ts:L7–L36`
- **Prompt-cache key / affinity:** `promptCacheKey` and `x-session-affinity` derive from the root session (children and forks share the parent's). `core/session/model-request.ts:L278–L295`; `core/session/affinity.ts:L6–L8`
- **Searchable memory for the model:** not found (no model-facing memory store; `core/environment/memory.ts` is an in-memory filesystem).

## Model interface
- **Streaming request:** the step calls `llm.stream(request, options)` and folds every `LLMEvent` through a publisher; it reads to the end "so the next request can reuse this response". `core/session/runner/step.ts:L103–L138`; client `ai/route/client.ts:L602–L607`, `L618–L622`
- **Request construction:** `LLM.request({model, http.headers, promptCacheKey, system, messages, tools, toolChoice, generation, providerOptions})` with `x-opencode-session-id`/`User-Agent` headers. `core/session/model-request.ts:L279–L302`
- **Wire format:** per-provider protocol modules (`anthropic-messages.ts`, `openai-responses.ts`, `bedrock-converse.ts`, `gemini.ts`, …) and framings (SSE) compile the canonical request and decode the stream. `ai/protocols/` (directory), `ai/route/client.ts:L423–L497`
- **Route/header hooks:** `session.model.request` may change `baseURL`/headers; `session.http.request`/`http.response` wrap the raw HTTP exchange. `core/session/model-request.ts:L305–L320`, `L337–L365`
- **HTTP timeouts:** headers 300 s, inter-chunk 900 s, whole-request none by default. `ai/route/transport/http.ts:L100–L146`; defaults `ai/schema/options.ts:L56`, `L62`
- **Stateful WebSocket transport:** bound per session when `model.transport === "websocket"`; rotates after 55 min, 15 s connect, 30 min idle; after 5 consecutive stream failures the session stays on HTTP. `core/session/model-request.ts:L368–L392`; `core/session/model-transport.ts:L22–L27`, `L186–L196`, `L308`
- **Error classification:** `isContextOverflowFailure` and `isRetryable` (rate limit, provider internal, transport unless delivery rejected, incomplete stream, unknown; `x-should-retry` header overrides). `ai/provider-error.ts:L72–L75`, `L81–L110`
- **Retry policy:** exponential from 2 s capped at 10 s per gap, 10 retries, jittered; provider `retry-after` honored up to 15 min; at most 3 timeout retries; `session.retry` plugin hook may override the decision. `core/session/runner/retry.ts:L31–L62`, `L64–L92`
- **Retry vs continue vs recover-full:** before output started → `Retry`; after output started on an interrupted stream → `Continue`; WebSocket `retry-full`/`rotate-and-retry-full` → `RecoverFull`. `core/session/runner/step.ts:L182–L204`, `L263–L271`, `L291–L295`
- **Unknown finish reason is an error:** turned into `InvalidProviderOutputError("incomplete-stream")`. `core/session/runner/step.ts:L171–L181`
- **Model resolution:** session model must be in the available catalog, else `ModelUnavailableError`. `core/session/runner/model.ts:L75–L91`
- **Token usage and cost:** normalized `input/output/reasoning/cache.read/cache.write`, cost by context tier. `core/session/usage.ts:L11–L19`, `L22–L36`
- **Vercel AI SDK bridge:** `AISDK.Service.model(RuntimeInfo)` wraps a `LanguageModelV3` as an `@opencode/ai` `LanguageModel` for third-party provider packages. `core/aisdk.ts:L237–L252`
- **Backup model for a request that could not be served (title only):** if the small model's attempt fails, the primary model is tried. `core/session/title.ts:L129–L133`

## Output
- **Streaming render path:** provider events are published as durable `Text.Started/Delta/Ended`, `Reasoning.*`, `Tool.Called/Progress/Success/Failed`, `Step.Started/Streamed/Ended/Failed`; deltas batched every 100 ms. `core/session/runner/publish-llm-event.ts:L443–L470`, `L106`, `L194–L200`
- **Concurrent tool execution from one response:** each `tool-call` event forks a fiber immediately; all are awaited after the stream ends. `core/session/runner/step.ts:L121–L134`, `L151`
- **Tool executor:** `execute.before` hook → input decode/validate → `tool.execute` → `execute.after` hook → content normalization (image resize). `core/tool.ts:L103–L156`, `L263–L284`; validation `core/tool/runtime.ts:L29–L61`, `L88–L100`
- **Shell tool:** 2-minute default timeout, `AGENT=1 OPENCODE=1` env, jobs with foreground block or background; no OS sandbox found, gating is by permission after tree-sitter parsing of the command into per-command resources and touched directories. `core/tool/plugin/shell.ts:L24`, `L117–L155`, `L199–L279`; parser `core/shell/parse.ts:L7`, `L392`
- **Edit tool asks with a diff preview:** `permission.assert({action: "edit", metadata: {files: [preview]}})` before applying. `core/tool/plugin/edit.ts:L271–L283`
- **Read/external-directory gating:** `authorizeRead` asks `external_directory` for paths outside the location, then `read` per file. `core/file-access.ts:L125–L142`, `L144–L161`
- **MCP tools as output:** each discovered MCP tool is registered under a server namespace, permission-asserted, then `callTool`. `core/tool/mcp.ts:L41–L77`
- **Code Mode `execute` tool:** the model submits JavaScript; tool calls inside it are routed through the same `executeTool` (hooks + permissions); `fetch` only, no imports/fs/timers. `core/codemode/tool.ts:L62–L69`, `L71–L108`; sandbox = custom tree-walking interpreter over acorn AST with value limits and optional timeout. `codemode/interpreter/execute.ts:L1`, `L56–L68`; `codemode/interpreter/limits.ts:L6–L13`
- **File-change artifact for the user:** a git-backed snapshot is captured before and after each step and the changed paths are attached to `Step.Ended`. `core/session/runner/step.ts:L74–L76`, `L234–L260`; `core/snapshot.ts:L43–L68`, `L90–L105`
- **Question tool shows a form:** `forms.ask` with one field per question, "Type your own answer" custom option. `core/tool/plugin/question.ts:L62–L112`, `L119–L132`
- **Tool failure settlement:** interrupted, declined, provider-failed, and result-missing calls are failed with distinct errors so no call stays unsettled. `core/session/runner/step.ts:L62–L64`, `L207–L232`

## Design decisions (one line each: the choice this harness made within a primitive)
- Input: every input, including harness-generated notices, is a durable inbox row with a `steer` (interrupt the current step boundary) or `queue` (next turn) delivery, promoted only at step boundaries under a per-session lock.
- Context: history is event-sourced and re-projected into model messages on every call; compaction is a summary message in that history (or an opaque provider checkpoint), triggered at ~90 % of the window using provider-measured counts plus a local estimate, with the newest 15k tokens kept verbatim.
- Model interface: an in-house canonical `LLMRequest` compiled per provider protocol, streamed over HTTP/SSE or a stateful WebSocket, with retry decisions split by whether output had already started.
- Output: tool calls are executed concurrently as they stream, every tool is permission-asserted inside its own code, most tools are reachable only through a single `execute` tool that runs model-written JavaScript in a custom interpreter.
- Control flow: one fiber per session drains a durable inbox; a step continues while tool calls were made, stops on a text-only finish, and is bounded by an optional per-agent step count; sub-agents are full child sessions (depth 1 by default) whose results come back as tool text or a synthetic message.

## Hard cases
- **Code Mode `execute` tool:** the model writes a program that sequences tool calls (`tools.ns["name"](input)`), which looked like control flow; rule "a program that sequences only tools is output" resolves it as output, and the interpreter cannot call the model (`core/codemode/tool.ts:L62–L69`). Its per-request catalog in the system prompt is context (`core/codemode/instructions.ts:L19–L30`).
- **`Permission.assert` lives inside each tool:** by file location it is output; by function it is an approval gate the harness consumes (the model never sees a plain decline, the step is interrupted), so it is control flow; the `"always"` rule save is persistence.
- **Question tool:** the form is output, the answers are input (the model consumes them), and a dismissal is treated like a permission decline (control flow) via the same defect tunnel (`core/tool/plugin/question.ts:L90–L97`).
- **Subagent tool:** the call is output; depth check, child creation, blocking and backgrounding are control flow; the child is a separate harness (`sessions.resume`); foreground results return as tool text, background results as a synthetic user message, which makes the same information input in one mode and output in the other.
- **Compaction service calls the model:** `SessionCompaction` decides when and what to summarize (context) but also issues `llm.stream` itself (`core/session/compaction.ts:L512`) and runs the retry policy (`L450–L459`). The brief says context "never calls the model"; resolved by assigning the trigger/split/budget to context, the summary request itself to model interface, and the `Compacted → re-attempt` loop to control flow. Partly DOES NOT FIT: native compaction (`L318–L332`) delegates context assembly to the provider, so the harness's context primitive holds only an opaque item it cannot inspect.
- **`MAX_STEPS_PROMPT` appended as an assistant message:** the step budget is control flow, but it is enforced by editing what the model sees (an assistant-role message plus `toolChoice: "none"`), so the mechanism straddles control flow and context (`core/session/runner/llm.ts:L240–L244`).
- **Instruction epochs:** changed AGENTS.md/date/env are frozen into durable `InstructionsUpdated` events rendered as system messages in the transcript; this is context, but it is implemented as persistence of history, and history is immutable, so stale instruction text stays in old events.
- **Plugin hooks (`session.context`, `session.model.request`, `http.request`, `tool.execute.before/after`, `permission.evaluate`, `session.retry`):** a single hook bus whose entries belong to five different primitives; decomposed by what each hook can change rather than where it is registered.
- **Durable event bus:** the same event log is persistence (projected into tables), observability (the trace), and the output channel (clients subscribe); the bus itself is out of scope as transport, its contents are assigned by what they record.
- **Title model fallback:** the "try the small model, then the primary" fallback (`core/session/title.ts:L129–L133`) is a backup model when a request could not be served (model interface), while choosing the small model in the first place is control flow.
- **WebSocket `RecoverFull`:** the transport reports it cannot replay an incremental exchange (model interface), but the decision to resend the full request is taken by the runner's outcome loop (control flow) (`core/session/runner/step.ts:L182–L188`, `core/session/runner/llm.ts:L324–L326`).
- **Synthetic messages:** "The server restarted…", "Your last response hit the output token limit…" are produced by control flow, admitted as input, and shown to the model as user-role messages; assigned as input with control-flow origin.
