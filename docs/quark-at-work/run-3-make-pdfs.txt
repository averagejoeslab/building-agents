# Quark Memory
- course: repo is "harness-engineering" (github building-agents), a hands-on course by Chase Dovey (Average Joes Lab) on building agents by building their harness; code MIT, content CC BY-NC-SA 4.0
- course: thesis is TokensOut = Model(TokensIn) and Agent = Harness(Model); harness = five primitives, control flow wrapping input, context, model interface, output
- course: lessons 1-4 are the primitives (the core); lessons 5-10 in production/ (observability, guardrails, sandboxing, resilience, performance, evaluation) are hardening layers that fold back into the primitives, not new primitives
- course: teaching method is take a thing apart by "what mechanistic primitive is it", then build up outward from the model; each lesson's quark.py is the previous one plus one primitive; lesson 4 quark.py is the finished harness
- course: every lesson README has the same layout: opening explanation, The worked example, Run it, Going further (other options, a product built on the primitive, a fuller example file), What to take away (The rule, "Notice what X never does", What's missing, link to next)
- course: setup is macOS or Linux, Python 3.13+, uv, ANTHROPIC_API_KEY in .env; run lessons with `uv run lessons/<n>/<file>.py` from repo root; from lesson 2 the agent runs model-written shell commands with no confirmation
- course: model used in all lessons is claude-sonnet-5-5 (opus-5-5 as backup in model_interface.py); max_tokens is 16384 everywhere, raised so thinking plus a tool request is not cut off
- lesson 1 (model interface): quark.py is 9 lines, one `call(**request)` wrapping client.messages.create, print of the response; model interface is the parentheses in Agent = Harness(Model); fields to read are content (blocks), stop_reason (end_turn vs max_tokens), usage (input_tokens, output_tokens incl. thinking)
- lesson 1 (model interface): model_interface.py adds timeout=120, max_retries=3, MODELS fallback list (sonnet-5-5 then opus-5-5) on APIConnectionError/RateLimitError/InternalServerError, streaming with get_final_message(), effort and thinking="summarized" settings; thinking text is empty by default, only a signature
- lesson 1 (model interface): gateways like LiteLLM and OpenRouter are the model interface as a product; ending point is both ends are stubs (hardcoded input, raw dump output)
- lesson 2 (input and output): taught together because they are two ends of one exchange through tools: the model asks (tool_use block), the harness acts, the result comes back as input (tool_result with tool_use_id); input is afferent, output is efferent
- lesson 2 (input and output): input.py has read() (prompt, blank line reprompts, Ctrl-D returns "/q") and input = argv or read; output.py loops over content blocks, prints text, runs tool_use via subprocess.run with stderr merged into stdout; quark.py combines both and builds input=[tool_result...] with "(exit N)" if empty
- lesson 2 (input and output): quark.py does one call only, so the model never sees the tool result; the gap is control flow; stop_reason tool_use means the model waits for a result
- lesson 2 (input and output): input_output.py is a Telegram bot (receive/send via getUpdates and sendMessage), tools bash and read_file via executors dict, asyncio.gather runs all tool requests at once, 30s bash timeout, is_error results, skips a tool_use cut off by max_tokens; MCP is output you plug in
- lesson 3 (control flow): control flow sequences the other primitives and terminates; shapes are run once, chat loop, workflow (code decides), agent loop (model decides)
- lesson 3 (control flow): quark.py adds `chat` flag, `messages` list and `while True`; if tool results exist append and continue, else hand back with read() or break; termination is the model not asking for a tool; there is deliberately no step limit
- lesson 3 (control flow): control_flow.py has MAX_STEPS=10 via for/else, a refusal stop_reason check, no chat mode, prints "[done in N steps]"; workflow.py is an evaluator-optimizer (draft, judge PASS, rewrite, max 3 rounds) where code decides order; LangGraph is the product example
- lesson 3 (control flow): lists Anthropic's Building effective agents workflows (prompt chaining, routing, parallelization, orchestrator-workers, evaluator-optimizer); the augmented LLM is not control flow (retrieval and memory are context, tools are output); routing stays control flow even to a cheaper model, unlike lesson 1's outage backup model
- lesson 3 (control flow): what's missing is context: the agent knows nothing about where, when, who, or past sessions, and messages grows unbounded
- lesson 4 (context): context assembles what the request holds and fits it in the window; components are instructions, working, episodic, semantic, procedural memory, retrieval, compaction, self-knowledge
- lesson 4 (context): quark.py is 234 lines, about 82 code plus a roughly 150-line system prompt (README says 152, file body is about 148); renames messages to working_memory and wraps call in try for BadRequestError "prompt is too long"
- lesson 4 (context): episodic memory is the harness writing every message via add() and remember() to .quark/episodes/<start>.jsonl, assistant output written before tools run; semantic memory is .quark/memory/memory.md and procedural memory is .quark/skills/*.md, both written by the model via bash commands given in the prompt, no memory code
- lesson 4 (context): skills() indexes skills from name and description headers into the prompt; mechanics() puts quark.py itself in the prompt with system() redacted; system prompt has Self Model, Memory (semantic, procedural, episodic, across), World Model, Other Selves Model, Body Operations, Mechanics; date only so cache_control caching hits
- lesson 4 (context): prompt teaches distill for facts and generalize for skills, recall ladder semantic then procedural then episodic, and "write memory only from what happened and what other selves told you"
- lesson 4 (context): compact() is lazy: on "prompt is too long" drop += 1, drop oldest turns, summarize the rest, replace working memory with the gist that points to the episode file; the model reads about a million tokens so it rarely fires
- lesson 4 (context): context.py alternates: fit() counts tokens against LIMIT=50_000 before each call and summarizes, trim() cuts long tool results (KEEP=4000), one shared .quark/episodes.jsonl, skills indexed by first line only
- lesson 4 (context): ends with "You've built a harness" and a sorting exercise for other harnesses (nanoagent is a TypeScript example); anything that decides what the model sees is context, acting on what the model said is output
- course: I verified every code block for lessons 1-3 and context.py match their files exactly, and the lesson 4 prompt matches quark.py apart from f-string brace escaping
- course: each lesson's closing "What's missing" chains the lessons: 1 stub input and output, 2 result never sent back, 3 knows nothing and grows unbounded, 4 is the finished harness

# The four memories

| Memory | Who writes it | Where | How the model sees it |
|---|---|---|---|
| Working | the harness, `add()` | `working_memory` | every call, as the messages |
| Episodic | the harness, `add()` | `.quark/episodes/<start>.jsonl` | by searching, when the past matters |
| Semantic | the model, with bash | `.quark/memory/memory.md` | by reading, when facts matter |
| Procedural | the model, with bash; indexed by `skills()` | `.quark/skills/<name>.md` | the index every call; a skill when it applies |

# The choices you make

The components listed at the top of this lesson are what context is made of; these are the choices you make when you build them.

- **Who decides what's remembered.** The model, writing it down when it thinks it matters, or harness code that saves and loads on its own.
- **What it retrieves.** Nothing, or documents, code or past messages found by search and put in the request.
- **When it fits.** After the API refuses, or before, by counting tokens against a limit.
- **How it fits.** Summarize old turns, drop them, or cut long tool results down before they're kept.
- **How it's laid out.** One system prompt, or instructions loaded only when a task needs them.
